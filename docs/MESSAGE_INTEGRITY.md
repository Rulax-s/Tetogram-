# Исправление идентичности и порядка: 0.2.1

База: master dfa54a2 (0.2.0), рабочее дерево перед изменениями чистое; origin/master совпал после fetch. Secrets не меняются. Новые функции не добавляются. Это исправление существующей линии 0.2.x, не новый проект и не переименование версии в 2.0.

## Подмена удалённых сообщений

В `ChatActivity.processDeletedMessages` локальный `MessageObject` из уведомления заменял исходный объект в массиве и индексах без `copyStableParams`. Конструктор оставляет `stableId=0`. Между тем `ChatActivityAdapter` вызывает `setHasStableIds(true)`, а `getItemId` возвращает именно `MessageObject.stableId`. Два одновременно удалённых сообщения получали один RecyclerView ID 0, несмотря на различные message ID, авторов и тексты в SQLite. Повторное связывание/анимация допускает ошибочное сопоставление ViewHolder. Обычная загрузка истории, напротив, назначает каждому объекту stable ID через штатный счётчик, поэтому повторный вход устраняет коллизию. Это подтверждённый дефект кода, соответствующий наблюдаемому симптому; трассировка на устройстве владельца не выполнялась.

Исправление: сверяется полный ключ account/dialog/message, для каждого фрагмента клонируются payload и TL Message, переносятся native `copyStableParams` и исходный stable ID. Для ещё не назначенного ID используется штатный уникальный счётчик. Payload уведомления не меняется: два открытых экземпляра чата не делят UI-объект. Массив, словарь, списки по дням, альбом/его positions/caption и существующие filtered-индексы обновляются согласованно. Данные SQLite не подменяются и не очищаются. Frozen snapshot адаптера остаётся штатным снимком, а не изменяется задним числом.

Стабильный adapter ID не заменяет Telegram message ID и не записывается в DB. Между Activity допустим новый набор adapter IDs; внутри одной Activity при замене идентичность строки сохраняется. Не используется глобальный ключ только по mid, не зависящий от диалога/аккаунта.

## Эфемерные сообщения

Реальный путь: `TL_updateNewEphemeralMessage` → `EphemeralMessagesHelper.convertEphemeralToFakeDefault` → MessageObject/ChatActivity. Серверный тип — TL_ephemeral.EphemeralMessage. В UI ID упакован с битами `0x60000000`, обычно остаётся положительным. Отдельная штатная таблица `ephemeral_messages` и её visibility/lifetime не менялись; архив удалённых сообщений такие сообщения исключает.

Обнаружены два места нарушения порядка:

1. `DeletedHistory.deliver` передавал смешанную страницу в `HistoryPagePolicy.trim`: обычная сортировка по ID воспринимала packed ephemeral ID как самый новый. Кроме того, он попадал в regular low/high bounds и обрезку страницы. При обратном порядке RecyclerView это меняло хронологическое положение после повторной загрузки.
2. Штатный live insert в ChatActivity сравнивал любые положительные IDs, в том числе packed ephemeral ID, как IDs одной последовательности. Эфемерное сообщение, доставленное позднее своей даты, могло вставляться перед более новыми обычными сообщениями. Условия по дате не отменяли уже истинное условие по ID.

Правило MessagesStorage вынесено без изменения семантики в `MessageTimelinePolicy.compare`: обычные положительные ID идут по убыванию, отрицательные — по штатному правилу; при участии ephemeral используются даты, при равенстве ephemeral перед обычным, два ephemeral — по возрастанию ID. То же правило применяется к live insert только для смешанных ephemeral-пар в обычном режиме. Scheduled/secret/quick replies и welcome-режим сохраняют свои ветки.

Overlay больше не пересортировывает весь исходный список: сохраняет его native порядок, выбирает курсорную страницу только по обычным положительным IDs, сохраняет ephemeral/pending строки и вставляет только локальные копии по штатному mixed comparator. Равные timestamps не теряют ID tie-breaker. Дополнительных сетевых запросов, изменения срока жизни и расширения видимости нет.

## Автоматические проверки и их границы

- DeletedRowPolicyTest: разные авторы/тексты при замене и repeated stable-ID binding, batch, независимые фрагменты, повтор удаления, нулевой ID, коллизии аккаунтов/диалогов, реконструкция модели.
- MessageTimelinePolicyTest: пять более новых сообщений после ephemeral, повтор merge, локальное удаление, одинаковые даты, несколько ephemeral, поздняя доставка, native storage order, page count/cursors, dedup, обычные ID при несовпадении часов.
- Существующие HistoryPagePolicyTest/HistoryPolicyTest и SQLite contract tests сохраняются.

Это автоматические тесты производственных Java policies и реальной SQLite-схемы, не Android instrumentation. Цикл связывания в тесте не является реальным RecyclerView, реконструкция модели — не реальный перезапуск Android. Ручной регрессионный план приведён ниже. Реальные сообщения/сессии в тестах не используются. Временные логи содержимого/идентификаторов не добавлялись.

## Ручная проверка на Android (пока не выполнена)

- [ ] Удалить два входящих сообщения разных авторов, затем batch; сравнить автора/текст/дату/статус после ожидания и обновления.
- [ ] Прокрутить вверх/вниз несколько раз, получить новые сообщения; копии не подменяются.
- [ ] Пересоздать Activity, повторно открыть чат, перезапустить процесс; копии и даты совпадают.
- [ ] Получить ephemeral от бота, затем пять обычных сообщений; положение ephemeral соответствует времени.
- [ ] Повторить после обновления списка, прокрутки, входа в чат и восстановления из SQLite.
- [ ] Несколько ephemeral подряд; одинаковые timestamps; delayed delivery; удаление соседнего обычного сообщения.
- [ ] Проверить исходную видимость «Видите только Вы», штатное удаление/срок жизни; никаких копий в архиве.
- [ ] Повторить в группе/канале, с двумя аккаунтами и одинаковыми IDs разных чатов; проверить replies, send, forward, уведомления, папки, secret chat, Mini Apps.

История редактирования в базовой master 0.2.0 отсутствовала и была явно недоступна; это исправление её не удаляет и не объявляет реализованной.
