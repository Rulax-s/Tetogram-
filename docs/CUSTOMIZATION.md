# Будущая модификация Tetogram

В версии 0.1.0 не добавляются новые пользовательские функции. Эта инструкция описывает порядок будущих изменений после получения рабочей базы.

1. Зафиксировать успешный workflow, SHA исходников/подмодулей, сертификат debug-ключа и результаты ручного тестирования. Отдельно хранить последний рабочий APK.
2. В отдельной ветке менять один UI-компонент или один поток. Карта файлов — `ARCHITECTURE.md`. Не переименовывать массово `org.telegram.*`: applicationId уже отделён от namespace.
3. Визуальные элементы выносить в небольшие классы под `org/telegram/ui/Components/tetogram/`, а будущие настройки — в отдельный класс/экран Tetogram. Эти каталоги пока не создают альтернативную архитектуру и не заменяют контроллеры Telegram.
4. Для новой настройки выбрать область: глобальная или конкретный аккаунт. Использовать отдельные имена ключей/файл preferences с префиксом `tetogram_`, определить default и миграцию. Не сохранять там копии auth keys, кодов входа или MTProto-сессий.
5. Подключать новые строки через стандартные `res/values` и `values-ru`, сохраняя остальные языки с fallback. Здесь строки дополнительно обрабатываются `buildSrc` в assets/localization; простое редактирование APK-ресурсов не всегда отражает runtime-перевод. Не менять stable resource ID генератор без необходимости.
6. Для цветов использовать `Theme` и существующий ResourcesProvider. Проверять пользовательские темы, тёмную тему, крупный шрифт, RTL и accessibility. Единственный фиксированный фирменный цвет в первой версии относится к собственной иконке.
7. Новое действие отправки проводить через существующий `SendMessagesHelper`/контроллер, подтверждение результата получать от сервера. Не изображать успешную отправку до серверного подтверждения и не добавлять фиктивные сообщения.
8. Сохранять account routing, подписки/отписки NotificationCenter, очереди UI/storage/network, отмену задач и recycle. Особенно осторожно менять `ChatMessageCell` и `ChatActivityEnterView`.
9. После изменения повторить статическую проверку, cloud build, проверку APK и затронутые пункты ручного чек-листа. Обновить CHANGELOG и известные ограничения.

Upstream обновлять отдельными merge/cherry-pick коммитами, сохраняя gitlink SHA подмодулей. При конфликте конфигурации не возвращать официальные API-данные, accountType, updater или логотип. После обновления сверять реальные SDK/NDK/JDK, tasks, generated strings и имена JNI-целей заново.

Passkeys, Firebase PNV, покупки Google Play, собственные карты и публикационная подпись требуют отдельных подтверждённых интеграций. Не включать их просто переключением флага и не обходить ограничения Telegram или Google. Существующие Premium-возможности аккаунта и протокол остаются upstream, но их работу нужно проверить на устройстве.

В 0.2.0 реализован namespace ui/tetogram и backend messenger/tetogram. Подключайте будущую историю редактирования к этому backend и существующей базе, не создавая параллельного хранилища. В текущей master до этой задачи backend v2 отсутствовал; интерфейс редактирования обозначен недоступным. Детали и ограничения — DELETED_HISTORY.md.

При модификации элементов чата сохраняйте native stable params при замене объектов и не делите mutable MessageObject между фрагментами. Используйте полный Telegram ключ account/dialog/message для сопоставления, а adapter stableId — только для UI. Учитывайте ephemeral ID namespace: видимость и TTL остаются у Telegram, локальный overlay не переупорядочивает серверную страницу. Исправления и тесты описаны в MESSAGE_INTEGRITY.md.

Для Reply на локально удалённые сообщения сохраняйте штатный composer и преобразуйте только outgoing-подготовку в SendMessagesHelper. Не сдвигайте исходные entities на месте: DeletedReplyProtocol сохраняет типы/metadata, а DeletedReplyPolicy учитывает UTF-16 и разделители. Не используйте удалённый ID как server reply target; сохраняйте native forum root, account/dialog и Telegram user ID владельца. Текст архива не копируйте в собственные настройки или вторую DB. См. DELETED_REPLIES.md.

С 0.2.4 formatEntities принимает исходный sender user ID и пригодный InputUser; outer blockquote содержит имя и snippet. Mention и bold полностью лежат в имени, body со своими entities начинается после одного переноса. Сохраняйте UTF-16 offsets и порядок quote → mention → bold. Без валидного user peer не создавайте @-заглушки, InputUserEmpty или ссылки на другого пользователя. Все проверки owner/account/dialog и native forum routing сохраняются.
